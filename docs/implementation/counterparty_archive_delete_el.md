# Αρχειοθέτηση και διαγραφή πελάτη ή προμηθευτή

Στην καρτέλα και στη λίστα ενεργών συναλλασσομένων εμφανίζεται πλέον το
κουμπί **Αρχειοθέτηση**. Ανοίγει οθόνη επιβεβαίωσης και διατηρεί το ιστορικό.
Αν υπάρχει ανοιχτή συμφωνία, εμφανίζεται η αιτία μαζί με σύνδεσμο στη συμφωνία
και η αρχειοθέτηση απαγορεύεται και στον server.

Εφάπαξ συμφωνία με πλήρως αντιστοιχισμένες χρεώσεις μπορεί να αρχειοθετηθεί.
Ενεργή μηνιαία χρειάζεται λήξη των όρων της, ακόμη κι αν έχει εξοφληθεί μέχρι
σήμερα. Ανεξόφλητες χρεώσεις, πρόχειροι/ανεπιβεβαίωτοι και προγραμματισμένοι
ενεργοί όροι κρατούν την εγγραφή ενεργή. Η απλή παλιά ένδειξη ολοκλήρωσης
δεν αντικαθιστά την πραγματική εξόφληση.

Για προβολή των αρχειοθετημένων, επιλέξτε **Κατάσταση → Αρχειοθετημένες
εγγραφές** στη λίστα. Εκεί διατίθεται **Επαναφορά**. Το ιστορικό τους
συνεχίζει να εμφανίζεται στις οικονομικές αναφορές.

Ο ενεργός ιδιοκτήτης του ίδιου γραφείου βλέπει επίσης **Διαγραφή** για
αρχειοθετημένη εγγραφή. Απαιτείται επιβεβαίωση και απουσία οικονομικού
ιστορικού. Ακόμη και ακυρωμένη/εξοφλημένη συμφωνία ή αυτοτελής κίνηση
αποκλείει τη διαγραφή. Ο απλός λογιστής δεν έχει αυτό το δικαίωμα.

Με τη διαγραφή αφαιρούνται τα στοιχεία ταυτότητας/επικοινωνίας και η καρτέλα
παύει να είναι διαθέσιμη από λίστες ή παλιούς συνδέσμους. Οι σημειώσεις και
το ίχνος ενεργειών διατηρούνται. Ο ιδιοκτήτης καταγράφεται στο ιστορικό
γραφείου με ημερομηνία server. Νέα εγγραφή με τον ίδιο Α.Φ.Μ. αποκτά
διαφορετική ταυτότητα και δεν κληρονομεί παλιές σημειώσεις.

## Εφαρμογή και έλεγχος από τον χειριστή

```bash
bash <<'SH'
set -euo pipefail
unzip -o ~/Downloads/accounting-platform-CR005-archive-delete.zip \
  -d ~/Downloads/accounting-platform-CR005-archive-delete
bash ~/Downloads/accounting-platform-CR005-archive-delete/APPLY_CR005.sh
cd ~/accountant_cloud/accounting_v5/accounting-platform
export PATH="$HOME/.local/bin:$PATH"
python3 tools/verify_cr005.py --record --host-dns
SH
```

Το APPLY εκτελεί μόνο Git/αρχεία και δεσμεύει αποκλειστικά τις επτά πραγματικές
αναφορές/δεσμεύσεις που διατηρήθηκαν από το επιτυχές CR004 και την αναβάθμιση
VM. Δεν ανακατασκευάζει το ιστορικό Git ούτε ανανεώνει παλιές δεσμεύσεις.

Ο έλεγχος χρησιμοποιεί νέα παραγωγική εικόνα, απομονωμένη PostgreSQL 17,
ολόκληρη τη σουίτα, τις 36 οικονομικές περιπτώσεις και τον πραγματικό worker
με Redis, επανάληψη μετά από απώλεια ACK και έναν scheduler. Οι migrations
0029/0030 εφαρμόζονται μόνο στο απομονωμένο περιβάλλον ελέγχου.

Η προετοιμασία του agent είναι στατική. Το υπάρχον VM παραμένει στην επιτυχώς
ελεγμένη έκδοση CR004 με 28 migrations μέχρι να ολοκληρωθεί ο νέος έλεγχος
και η αντίστοιχη αναβάθμιση. Οι λογαριασμοί, το MFA, τα κλειδιά και οι
85 πλήρεις αποδοχές παραμένουν ως είχαν. Το νέο αποτέλεσμα δεν αποτελεί
αποδοχή λογιστή ή άδεια πραγματικής παραγωγικής χρήσης.
